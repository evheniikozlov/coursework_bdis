# Лабораторна з контейнеризації — детальні інструкції

Мета: вручну зібрати власний Docker-образ з кодом, запустити з нього
контейнер, окремо запустити контейнер БД, зв'язати їх по мережі,
переконатись, що з коду можна записати й прочитати дані в БД, і
побачити результат через логи — причому логи мають зберегтись на
вашому комп'ютері навіть після видалення контейнера.

Усе показано на прикладі **PostgreSQL** (реляційна БД — дозволено
завданням і найпростіша для демонстрації). Весь код лежить у
`docker-lab/app/`.

---

## 0. Передумови

Перевірте, що Docker встановлено і демон запущений:

```bash
docker --version
docker ps
```

Якщо `docker ps` видає помилку про доступ — на Linux додайте
користувача в групу `docker` (`sudo usermod -aG docker $USER`, потім
перелогінитись), або запускайте команди з `sudo`.

Перейдіть у папку лабораторної:

```bash
cd docker-lab
```

Структура, яку ви маєте (файли вже згенеровано):

```
docker-lab/
├── app/
│   ├── Dockerfile
│   ├── requirements.txt
│   ├── demo_app.py
│   └── .dockerignore
├── logs/                      # <-- сюди писатимуться логи з хоста
├── docker-compose.lab.yml     # альтернатива ручним командам (кроки 1-6)
└── docker-compose.full-platform.yml   # повна схема проєкту (не для лаби)
```

## Варіант А: вручну через `docker build` / `docker run` (рекомендовано — саме так "попрацювати з контейнерами")

### Крок 1. Створити окрему мережу Docker

Без цього два контейнери не "побачать" один одного за іменем.

```bash
docker network create podcast-net
```

Перевірка:

```bash
docker network ls
```

Має з'явитись рядок `podcast-net`.

### Крок 2. Запустити контейнер БД (PostgreSQL)

```bash
docker run -d \
  --name podcast-db \
  --network podcast-net \
  -e POSTGRES_DB=podcast_demo \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -p 5432:5432 \
  postgres:16
```

Пояснення прапорців:
- `-d` — запустити у фоні (detached).
- `--name podcast-db` — ім'я контейнера; за цим іменем його знаходитиме наш app-контейнер (Docker DNS всередині мережі `podcast-net`).
- `--network podcast-net` — підключити до нашої мережі.
- `-e ...` — змінні оточення офіційного образу `postgres`, якими він сам створює БД/юзера при першому запуску.
- `-p 5432:5432` — прокинути порт на хост, щоб за бажання підключитись звідти (напр. через `psql` чи DBeaver); для зв'язку між контейнерами це не обов'язково.

Перевірте, що контейнер піднявся і БД готова:

```bash
docker logs podcast-db
```

У логах має з'явитись рядок на кшталт `database system is ready to accept connections`.

### Крок 3. Зібрати свій образ із кодом

```bash
docker build -t podcast-demo-app:1.0 ./app
```

Що відбувається: Docker читає `app/Dockerfile`, бере базовий образ
`python:3.12-slim`, встановлює залежності з `requirements.txt`,
копіює туди `demo_app.py` — і зберігає все це як образ з тегом
`podcast-demo-app:1.0`.

Перевірка, що образ з'явився:

```bash
docker images | grep podcast-demo-app
```

### Крок 4. Підготувати папку для логів на хості

```bash
mkdir -p logs
```

Ця папка (`docker-lab/logs`) буде змонтована всередину контейнера як
том (volume) — усе, що застосунок пише у файл `/app/logs/app.log`
всередині контейнера, фізично опиниться у файлі
`docker-lab/logs/app.log` на вашому диску.

### Крок 5. Запустити контейнер зі своїм кодом, підключений до БД

```bash
docker run \
  --name podcast-app \
  --network podcast-net \
  -e DB_HOST=podcast-db \
  -e DB_PORT=5432 \
  -e DB_NAME=podcast_demo \
  -e DB_USER=postgres \
  -e DB_PASSWORD=postgres \
  -v "$(pwd)/logs:/app/logs" \
  podcast-demo-app:1.0
```

Пояснення:
- `--network podcast-net` — той самий network, що й у БД; завдяки
  цьому ім'я `podcast-db` (значення `DB_HOST`) резолвиться Docker'ом
  у внутрішню IP-адресу контейнера БД.
- `-e DB_HOST=podcast-db` — **ось тут відбувається "зв'язування"**
  контейнерів: застосунок підключається не по IP, а по імені
  контейнера БД.
- `-v "$(pwd)/logs:/app/logs"` — **ось тут відбувається персист
  логів на хост**: ліва частина (`$(pwd)/logs`) — реальна папка на
  вашому комп'ютері, права (`/app/logs`) — шлях усередині контейнера,
  куди пише `demo_app.py` (через `logging.FileHandler`).

Без `-d` контейнер запуститься у forground-режимі — одразу побачите
логи в терміналі. Скрипт з'єднається з БД, створить таблицю, запише
один запис, прочитає всі записи і завершиться.

### Крок 6. Перевірити результат трьома способами

**а) Логи самого контейнера (поки він існує):**

```bash
docker logs podcast-app
```

**б) Файл логів, що лишився на хості (переживе видалення контейнера):**

```bash
cat logs/app.log
```

**в) Безпосередньо запит до БД, щоб переконатись, що дані справді там:**

```bash
docker exec -it podcast-db psql -U postgres -d podcast_demo \
  -c "SELECT * FROM episodes_demo;"
```

Ви маєте побачити рядок з `episode_id = ep-docker-lab-001`.

### Крок 7. Довести, що логи переживають видалення контейнера

```bash
docker rm podcast-app
cat logs/app.log
```

Файл і далі читається — контейнера вже немає, а лог залишився на
диску. Це і є доказ персистентності логів для звіту (можна додати
скріншот цього кроку).

### Крок 8 (опційно). Прибрати все за собою

```bash
docker rm -f podcast-db
docker network rm podcast-net
docker rmi podcast-demo-app:1.0
```

(`logs/app.log` при цьому нікуди не зникає — він живе на хості
незалежно від контейнерів та образів.)

## Варіант Б: той самий результат одним файлом (`docker compose`)

Якщо хочете показати в звіті також декларативний спосіб (а не лише
ручні команди):

```bash
docker compose -f docker-compose.lab.yml up --build
```

Це піднімає обидва контейнери, будує образ застосунку, зв'язує їх
через внутрішню мережу `lab-net`, і монтує той самий том для логів.
Логи так само опиняться у `docker-lab/logs/app.log`.

Зупинити й прибрати (разом з даними БД):

```bash
docker compose -f docker-compose.lab.yml down -v
```

> Compose — це декларативний опис того самого, що ви вручну зробили
> у Варіанті А. Для звіту варто продемонструвати Варіант А (ручні
> команди — показує розуміння окремих примітивів Docker: images,
> containers, networks, volumes), а Варіант Б згадати як те, до чого
> це природно масштабується в реальному проєкті.

## Що взяти у звіт

1. **Скріншот/вивід команд** із Кроку 5 (запуск) і Кроку 6 (три
   перевірки — docker logs, cat файлу, SELECT у БД).
2. **Скріншот Кроку 7** — `docker rm` + `cat logs/app.log` все ще
   працює → доказ персистентності логів через volume.
3. Короткий опис (2-3 речення): яку мережу, образ, контейнери й
   volume ви створили і навіщо кожен з них.
4. Посилання на `docker-compose.full-platform.yml` як ілюстрацію, як
   та сама техніка (networks + volumes) масштабується на всю
   архітектуру курсової (Mongo + Elasticsearch + Neo4j + Redis +
   backend).

Текст-обґрунтування для самого звіту (розділ "Контейнеризація") і
оновлена архітектурна схема — у файлі
`../containerization_report_section.md`.
